Adding AnimationEvents to a Frank Slash Pack FBX clip (e.g. Katana S1_Attack01/02/03). Two coupled importer gotchas bit hard (2026-06-18, KatanaMelee combo wiring) — burned several iterations.

**★Gotcha 1 — FBX event `time` in the .meta is stored NORMALIZED [0..1], importer multiplies by clip length on import.** Verified on Frank Katana Attack01 (len 1.25s): meta `time: 0.342` → runtime event @0.4275s (0.342×1.25). So to land an event at absolute second `T`, write `time: T / clipLength` in the meta. Table used (all 3 land exactly): Attack01(1.25s) hit 0.428→meta 0.342, window 0.50→0.40, end 1.15→0.92. Attack02/03(1.333s) end 1.227→meta 0.92, etc. (0.92 = 92% end-marker, same normalized value across clips since it's a fraction.)

**★Gotcha 2 — `ModelImporter.clipAnimations = new ModelImporterClipAnimation[]{...}; SaveAndReimport()` EXPANDS clip length.** Even with explicit firstFrame=0/lastFrame=75, rebuilding the clipAnimations array programmatically made the take import at FULL length (1.25→1.4375s, ×1.15; 1.333→1.636, ×1.227) AND re-scaled event times. Root cause: pack uses `avatarSetup: 2` (CopyFromOther avatar) + empty `importer.clipAnimations` (auto clips); the reconstructed array lost the trim binding. **DO NOT build clipAnimations in code for these.**

**✓ Correct path = edit the `.FBX.meta` clipAnimations `events:` block DIRECTLY with the Edit tool, then `AssetDatabase.ImportAsset(path, ForceUpdate)`.** This preserves length (no take expansion) and applies the normalized→absolute scaling predictably. This is also how the project's pre-existing Attack01 hit event was placed (it worked).

**★Update 2026-06-19 — Gotcha 2 has a SAFE in-place variant + Bake-Into-Pose field mapping.** When you must change *import flags* (Bake Into Pose) not just events, do NOT hand-edit the meta with guessed field names. The Bake Into Pose flags are NOT `lockRoot*` in YAML — the `ModelImporterClipAnimation` API props map to `loopBlend*` meta fields:
- `clip.lockRootRotation = true`  → meta `loopBlendOrientation: 1`  (Bake Rotation into Pose ON — kills facing drift; correct for attacks since code owns aim)
- `clip.lockRootHeightY = true`   → meta `loopBlendPositionY: 1`    (Bake Y into Pose ON — grounded)
- `clip.lockRootPositionXZ = false` → meta `loopBlendPositionXZ: 0`  (Bake XZ OFF — root forward translation PRESERVED)
The *safe* mutation = `var clips = imp.clipAnimations; if(empty) clips = imp.defaultClipAnimations;` then set props on the **existing** element, `imp.clipAnimations = clips; SaveAndReimport()`. This is in-place (keeps firstFrame/lastFrame trim binding) → **no length expansion** (verified: 60/68/63 frames survived). The expansion in Gotcha 2 was caused by *constructing fresh* `new ModelImporterClipAnimation[]{}` which loses the take trim — mutating the materialized existing array is fine. Events placed via direct meta-edit also SURVIVE this reimport (verified: intParameter+times intact). So: events = direct meta Edit; import flags = importer API in-place mutate. Both in one reimport is OK.

**Reversion note:** Frank_Slash_Pack is **git-untracked** (added this session) → can't `git checkout` a corrupted .meta. The original meta values are the only backup; capture them via Read BEFORE editing. Pristine pack clips ship with `events: []` and `maskType: 1`.

**Benign warning to ignore:** every reimport logs "Rig Error: Copied Avatar Rig Configuration mis-match. Bone length ... position error = N mm" (thigh/hand/etc., <6mm) + "translation animation will be discarded". This is the standard Frank copy-avatar + translation-DOF-discard warning ([[project_frank_slash_retarget_gate]]), NOT caused by event edits. unity-mcp RunCommand reports the whole command as `success:false` when ANY warning fires — read the `[Log]` lines; the work usually succeeded.

**Blade-impact frame measurement (how hit frames were chosen):** instantiate `Frank_Katana_Skin.FBX`, `clip.SampleAnimation(inst, t)` per frame, read `Weapon_Blade` bone world pos, compute per-frame speed. Peak blade speed = the cut. Bone telemetry is reliable per-step ([[feedback_editmode_capture_one_pose_per_invoke]] — only SkinnedMesh render is stale, not bone transforms). Measured: Attack01 down-diag cut @f26, Attack02 deep downward chop @f26, Attack03 upward finisher @f32. Good 3-beat combo shape.

**★Update 2026-06-20 — Counter(반격) state motion swap Skill02→Attack02 + two new lessons.** Swapped player `Counter` Animator state (KatanaMelee.controller fileID 1112000000000000002) motion guid only (Skill02 `3a3b771c...`→Attack02 `a1926410...`; clip fileID stays shared `1827226128182048838`). tag `Action` survives swap (verified — busy-leak guard intact). Events on Attack02: OnAttackHit(int 0)@norm0.31, OnComboEnd@norm**0.87**. Bake T/T/F. Length 1.3333 preserved.
- **★LESSON A — OnComboEnd (clip-end terminator) must fire BEFORE the state's exit-time, not after.** Counter→Locomotion transition = `m_HasExitTime:1 exitTime:0.9 duration:0.1 m_HasFixedDuration:1` (duration is **0.1 SECONDS** not normalized when HasFixedDuration=1). Stab(MUST-FIX) vs Codex(not-required) **diverged**: Codex's pipeline analysis (`ProcessGraph`→`FireAnimationEventsAndBehaviours`, source state keeps dispatching during blend-out) says an event at norm 0.92 (>exit 0.9) *probably* fires; Stab says the 0.02-norm (~1.6 frame @60fps) margin is frame-rate-fragile and Unity docs "events after exit time MIGHT not fire." **Resolution = place the terminator BEFORE exitTime** (0.92→0.87): converts "probably" → "GUARANTEED fires while sole current state," zero feel cost (recovery static by norm 0.85), and stays in-scope (touch only the event, NOT the transition). General rule: clip-end OnComboEnd/terminator norm should be < the state's outgoing exitTime norm. (Skill02 had 0.92 with same transition and apparently worked via the 3.5s watchdog/self-heal reconcile catching misses — but the clean terminator firing is the whole point; don't lean on the watchdog.)
- **★LESSON B — Frank clips are PURE Humanoid: NO generic Weapon_Blade transform curves exist** (137 bindings = all MotionT/Q·RootT/Q·LeftFootT/Q·RightHandT/Q muscle/IK-goal curves). So the §"Weapon_Blade SampleAnimation" method from 06-19 **FAILS on these Root_Motion FBX clips** — `clip.SampleAnimation(inst,t)` AND `Animator.Update(dt)` BOTH return stale (all 0.00 m/s) in edit mode (no play mode → pose graph doesn't evaluate). **Working measurement = read the humanoid `RightHandQ.xyzw` curves directly** (`AnimationUtility.GetEditorCurve`), evaluate the quaternion per frame, compute `Quaternion.Angle(q[i],q[i+1])/dt` = hand-goal angular velocity. The sword is rigid in the right hand so its sweep tracks RightHandQ. Attack02 strike = single dominant spike norm 0.30 (2328 deg/s, hand linVel 7.81 m/s), motion settles by 0.35 → contact = norm ~0.31. (The 06-19 Weapon_Blade method may have only worked because it sampled a *skin* FBX that carries generic weapon-bone curves; these Root_Motion FBX don't.)
