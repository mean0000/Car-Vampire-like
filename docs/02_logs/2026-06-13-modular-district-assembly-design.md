## ★0. 이 문서가 직전 방사 설계와 어떻게 다른가 (필독 — 정직한 위상 변경)

직전 산출물 `2026-06-13-first-stage-district-design.md`는 **고정 한 장(hand-placed single layout)** 전제였다: 동심원 3띠·추출구 3종·고가 잔해·인카운터 D1~D7이 *정해진 좌표*에 박힌 한 장의 구역. 그건 그것대로 옳지만, 유저가 그 뒤 확정한 최종 구조와 **위상이 다르다**:

> "지루함 방지 = 모듈 라이브러리 + 절차 조립. 고정 한 장 ❌ → 손제작 도심 청크 + 매 런 다른 조립 = 매번 다른 오픈 존. 절차생성 ≠ 던전(오픈 존을 *조립*하는 기법, Hades·Dead Cells·뱀서 솔로 증명)." (← `project_2026_06_13_run_structure_pressure_engine` 맵 구조 최종 확정)

| 항목 | 직전(고정 한 장) | 본 문서(모듈 조립) | 근거 |
|---|---|---|---|
| **레이아웃** | 정해진 좌표 1장 | **유한 모듈 라이브러리 → 매 런 규칙 조립** | ← 유저 확정(run_structure 맵구조) |
| **재플레이성** | 매 런 동일 공간 | **매 런 다른 오픈 존(읽힘은 유지)** | ← Hades/Dead Cells/뱀서 솔로 증명 |
| **솔로 비용** | 한 장 손배치 N일 | **모듈 세트 1회 + 조립 규칙 → 바이옴 재사용으로 분할상환** | ← 유저 "앞단 더 들어도 총 수고 덜 듦" |
| **던전화 위험** | 없음(오픈) | **여전히 오픈 존**(방·복도 진행 ❌, 조립만 절차) | ← run_structure "절차생성 ≠ 던전" |

**계승(직전 방사 설계에서 그대로 가져옴):**
- 동심원 깊이(중앙 코어 고밀도·고노출·LV4피크 ↔ 외곽 저밀도·안전·추출구) — ← Duckov 동심원
- 비대칭 추출구 3종(X1 개방 / X2 키 / X3 플레어+대기) — ← Duckov 추출구 3종
- 고가 잔해 랜드마크(정위치 1개) — ← 레퍼 §4 메모러블 피처
- 인카운터 동사(대시 처단·돌파·매복·무리 끊기), 시야 콘 = 매복 발생기 + 전방 학살 가시화
- 키트 실선별(BR 도로/건물 + Construction 콘크리트, PolygonGeneric 판타지 배제)
- NavMesh 함정 목록(이음새 0.01u 갭 등)

**바뀌는 것은 "공간을 어떻게 만드느냐"뿐**: 직전 = 한 장을 손으로 그림 / 본 문서 = 모듈을 만들고 규칙으로 매번 조립. **동심원·추출구·랜드마크·인카운터·키트는 이제 "고정 좌표"가 아니라 "조립 규칙이 보장하는 불변식"으로 재해석된다.**

⚠️ **반려 위험 차단**: 직전 *고정* 방사 설계가 "공간 위상은 맞는데 매 런 같아서 지루"가 반려 사유라면 본 모듈 조립이 정답이다. 반대로 *고정 한 장이 오히려 좋았다*면 — 그건 §8 P0에서 유저가 갈라줘야 한다.

## 1. 모듈 타입 세트 (도심 청크 라이브러리)

### 1.0 설계 원칙 (모듈을 어떻게 쪼개나)

레퍼런스가 가리키는 모듈화 방식은 **"고정 골격 + 절차 채움"**(Zero Sievert) — 완전 손배치도 완전 절차도 아닌 중간이다(← 레퍼 §3). 그래서 모듈을 두 결로 나눈다:

- **(A) 구조 모듈** = 바닥·도로·벽·건물 외관 = *공간을 정의*. 절차 조립이 이걸 그리드에 배치. **유한 라이브러리 = 솔로 친화**(Hades도 방 풀이 유한).
- **(B) 드레싱 모듈** = 차량·바리케이드·잔해·컨테이너·매복 가림막 = *구조 모듈 위에 절차 산포*. 같은 거리 모듈도 드레싱이 달라 다르게 읽힘(← Zero Sievert 절차 디테일).

**그리드 기준 = 10m**(← 직전 빌드 스펙들이 쓴 10m 격자 + Synty 도로 조각이 5m·10m·20m 배수 = 10m가 최소공배수). 모든 모듈 풋프린트 = 10m 배수. **이유**: 엣지 스냅이 그리드 정렬로 단순해지고, NavMesh 이음새 정렬도 그리드가 강제한다(0.01u 갭 함정 차단).

⚠️ **치수 출처**: BR `SM_Env_Road_Straight_*` = 20(폭)×0.7×5(깊이), BR `SM_Env_Bridge_01/02` = 11×2.8×5, Construction 콘크리트 바닥/벽 = Y=0 (← `feedback_synty_city_composition` 실측 + `2026-06-13-first-stage-district-design.md` §5). **광장 바닥 = `SM_Env_Road_Cross_01`(교차로) 또는 Construction `SM_Bld_Concrete_Floor_01~04` 타일링**(직전 설계 계승).

## 2. 연결 규칙 (모듈이 어떻게 스냅되나)

### 2.1 엣지 소켓 규약 (그리드 스냅)

각 모듈 외곽은 10m 그리드 셀로 나뉘고, 셀 경계마다 **엣지 타입** 하나를 가진다:

| 엣지 타입 | 의미 | 무엇과 연결되나 |
|---|---|---|
| **ROAD** | 차도/거리 개구부(폭 매칭 필요) | ROAD ↔ ROAD (폭 등급 일치) |
| **WALL** | 건물 외피/봉쇄벽(닫힘) | 아무것과도 통행 안 됨(벽끼리 인접 OK) |
| **OPEN** | 광장/개활지 가장자리(자유 통행) | OPEN ↔ OPEN, OPEN ↔ ROAD |
| **ALLEY** | 좁은 길 개구부(폭 6) | ALLEY ↔ ALLEY, ALLEY ↔ OPEN |

**조립기는 인접 모듈의 맞닿는 엣지 타입이 호환될 때만 스냅한다.** ROAD↔WALL은 불법(거리가 벽으로 막힘) → 조립 규칙이 거부.

### 2.2 Synty 타일링 규칙 계승 (★권위: `docs/00_authority/2026-06-03-synty-demo-placement-rules.md`)

모듈 *내부* 프리팹 배치는 이미 검증된 규칙을 그대로 따른다 — 새 연결 물리는 만들지 않는다:

- **도로 직선**: `SM_Env_Road_Straight_*`(20폭×5깊이) = rotY=0 유지, 진행축으로 5m 간격 적층. E-W는 rotY=90. **90도 돌려 얇은 차선처럼 쓰지 말 것**(피벗 어긋남). (← `synty_city_composition` BR 도로 타일링)
- **코너 연결**: bbox 바깥 모서리 맞대기(차도는 bbox 바깥 모서리에 붙음). 폭 등급 일치. (← `tooncity_road_rules` 곡선 연결)
- **건물 어깨맞대기**: 거리 모듈 가장자리에 건물 외관을 셋백 0으로 바짝 → "거리 복도" 형성. (← `synty_city_composition` Western 타운)
- **지면 = 절대 Unity Plane 아님**: 모듈 바닥 = 팩 지면 메시 타일(Construction 콘크리트 바닥 또는 BR 도로 메시). **전부 Y=0**(off-zero-Y 함정). (← `synty_city_composition` 슬랩 사고)
- **다리(고가 잔해)**: `SM_Env_Bridge_Broken_01` + Support 기둥(y−2.7). (← `synty_city_composition` 다리 타일링)

### 2.3 NavMesh 이음새 = #1 검증 체크포인트

모듈이 그리드 스냅돼 *시각적으로* 닿아도 ~0.01u 갭이 남으면 NavMesh 연결이 끊겨 적이 맵 전체를 빙 돌게 된다(← LevelDesign 정의 #1 함정). **그리드 스냅이 이걸 1차 방어**(정수 그리드 좌표 강제)하지만, 모듈 경계 바닥 메시가 미세하게 안 닿을 수 있다. → **조립 후 모든 인접 모듈 경계에서 NavMesh 연결성 검증 필수**(Gameplay가 베이크+검증, 본 문서 §9 V1). **모듈 바닥 메시는 경계에서 0.5m 오버랩 권장**(갭 대신 겹침 = 안전).

## 3. 절차 조립 알고리즘 (규칙 — 코드 아님, 설계 명세)

> **이 절은 "어떤 규칙으로 매 런 코히어런트한 바운디드 오픈 존을 짜는가"의 설계 명세다. 실제 C# 구현 = Gameplay 핸드오프(§8). 본 문서는 규칙·불변식·시드만 정의.**

### 3.0 입력·출력

- **입력**: 시드(정수, ← `project_2026_06_13_run_structure` 변주 + LevelDesign이 시드 *값* 소유 / Gameplay가 소비), 바이옴 id(키트 스왑용 §5), 동심원 반경 파라미터.
- **출력**: 90×90m 바운디드 오픈 존 1장 = {모듈 인스턴스 배치 + 띠 메타 + 추출구 3종 위치 + 스폰 출처 마커 분산 + 랜드마크 위치}.

### 3.1 조립 7단계 (순서 = 불변식 우선순위)

```
1. 동심원 띠 골격 깔기   → 코어(A) 1셀군 중앙 고정, 중간(B) 링, 외곽(C) 링, 봉쇄(W) 최외곽
2. 코어 M1 + 랜드마크 M8 정위치   → 중앙은 항상 코어 광장, 고가 잔해 부착(정위치 1개)
3. 중간 띠(B) 거리망 조립   → M2/M3/M4를 ROAD 엣지 매칭으로 코어에서 외곽으로 방사, 다중 경로 보장
4. 외곽 띠(C) 채움   → M5/M6/M7을 거리 끝에 부착, 막다른 골목은 M6(방) 또는 추출구로만 종결
5. 추출구 3종 비대칭 배치   → X1/X2/X3를 외곽 모서리 서로 다른 3방향에 분산(§3.2)
6. 스폰 출처 분산 + 디제틱 시그니처   → 문/창/잔해/하수구 스폰 마커를 띠별 인구예산 따라 산포(§3.3)
7. 드레싱 절차 산포   → 차량/바리케이드/컨테이너/잔해를 구조 모듈 위에 시드 기반 배치(§3.4)
```

### 3.2 불변식 (조립이 *반드시* 지켜야 할 6규칙)

매 런 레이아웃이 달라지되 아래는 항상 참 — 이게 "달라도 읽힘"의 핵심:

| # | 불변식 | 왜 (위반 시 깨지는 것) | 출처 |
|---|---|---|---|
| **I1** | **동심원 띠 항상 보장**: 중앙=코어(고밀도/노출/보상), 외곽=안전/빈약 | 위반 시 깊이=위험=보상 무너짐 → 욕심 루프 죽음 | ← Duckov 동심원 |
| **I2** | **추출구 3종 외곽 비대칭 분산**: 서로 다른 3방향, 코어에서 ≥1개 경로 | 한곳에 몰리면 추출 결정(어느 방향 누빌지)이 무의미 | ← Duckov 추출구 3종 + Zero Sievert 경계 |
| **I3** | **디제틱 스폰 출처 분산**: 정면 팝인 금지, 문·창·잔해·등뒤 텔에서만 | 정면 팝인 = 매복 긴장 죽음 + 출처 단일 가독성 깨짐 | ← run_structure 젠 모델 |
| **I4** | **랜드마크(고가) 정위치 1개**: 코어에 부착, 매 런 같은 위치 | 정위치 앵커 없으면 미니맵 없이 방향 못 잡음 | ← 레퍼 §4 메모러블 피처 |
| **I5** | **자유 누비기 + 다중 경로 + 막다른 데스트랩 0**: 모든 추출구 ≥2 경로, 막다른 골목은 방/추출구로 종결 | 데스트랩 = 호드에 갇혀 죽음(불공정) / 단일 경로 = 예측성 | ← Zero Sievert 다중 접근 + 액션 앵커 |
| **I6** | **읽힘 유지**: 밀도 40/30/30 공간 분포, 색대비(차폐 더 어둡게), 평면 반복 금지 | 평면 반복 = 호평작도 약점(Death Must Die 반례) | ← 레퍼 §4 craft + §5 반례 |

### 3.3 스폰 출처 분산 규칙 (디렉터 ≠ 트레드밀)

직전 젠 모델 계승(← `project_2026_06_03_spawn_model` + run_structure 젠): 띠별 유한 사전배치 + Dormant 디제틱 깨움. 조립은 **스폰 마커를 모듈의 디제틱 출처에 부착**한다:

- 각 M6(진입 건물) = 문/창 스폰 마커 1~2 (등 뒤/측면 매복).
- 각 M8(고가 잔해) 아래 = 콘 차단 매복 포켓 1.
- 각 거리 모듈 = 차량/잔해 뒤 매복 포켓 0~1 (드레싱과 연동).
- **띠별 인구 예산**(← spawn_model): A 고 / B 중 / C 저. 조립이 마커 수를 예산 상한으로 캡.
- ⚠️ **스폰 마커 최소 분리 1.5m**(35+ 동일점 코로케이트 = 오버랩 폭발 ← LevelDesign 함정). 조립이 강제.

### 3.4 드레싱 절차 산포 규칙

- 시드 기반 결정론(같은 시드 = 같은 드레싱, 재현 가능).
- 차량/컨테이너 = "의미 있는 무리"로 군집(하나씩 흩뿌리지 않음 ← `synty_city_composition` 프롭 군집).
- 매복 가림막은 콘이 안 덮는 측면/후방에만(45° 부감 = 3m 벽이 1.9m만 가림 ← 공격 문법 전제). 직전 설계 P1~P4 매복 포켓 기하 계승.
- **드레싱 밀도가 페이싱을 직접 결정**(40% 개방/30% 중밀도/30% 밀집 ← 레퍼 §4). 조립이 띠별로 차폐 밀도를 비율 배분.

### 3.5 솔로 친화 = 유한 라이브러리 재사용

- 조립기는 **새 지오메트리를 만들지 않는다** — 손제작 모듈을 *재배치*만. 모듈 풀이 유한해야 솔로가 감당(← Hades/Dead Cells/뱀서 증명, run_structure).
- 새 바이옴 = 새 조립기 아님. **같은 조립 규칙 + 키트 스왑**(§5). 그래서 "앞단 더 들어도 총 수고 덜 듦"(유저).

## 4. 변주 4겹 매핑

run_structure가 확정한 변주 4겹을 본 모듈 시스템의 어느 레버가 담당하는지 매핑:

| 변주 겹 | 담당 레버 | 매 런 무엇이 달라지나 | 비용 |
|---|---|---|---|
| **1. 레이아웃 조립** | §3 조립 알고리즘 + 시드 | 거리망·추출구 위치·골목 배치·드레싱 산포 | 시드만 바꾸면 공짜(라이브러리 1회 비용) |
| **2. 내용(적·전리품·이벤트)** | 스폰 출처 마커 + 인구 예산 + 현장 이벤트 | 어느 출처에서 뭐가 나오나, 보급 투하/폭격 위치 | 인카운터 SO 데이터(Gameplay 튜닝) |
| **3. 빌드(로그라이트)** | (LevelDesign 밖 — 레벨업 카드) | 내 무기·능력 빌드 | ← `project_2026_05_31_levelup_catalog` |
| **4. 바이옴 로테이션** | §5 키트 스왑 | 같은 조립 규칙, 다른 외관(폐허도시→평원→사막…) | 키트 세트 1개/바이옴 |

★ **곱셈 효과**: 레이아웃(무한 시드) × 내용(스폰 데이터) × 빌드(카드) × 바이옴(키트) = 적은 손제작으로 큰 변주 공간(← Hades/Dead Cells 솔로 증명 방식).

### 5. 바이옴 간 모듈 재사용 전략 (키트 스왑)

run_structure: "라이브러리가 바이옴 재사용." 모듈 **타입·풋프린트·엣지 규약·조립 규칙은 바이옴 불변**, 키트(외관 프리팹)만 스왑:

| 모듈 타입 | 폐허 도심(1차) | 평원/사막(후속 — 키트만 스왑) | 출처 |
|---|---|---|---|
| M1 코어 광장 | BR 교차로/Construction 콘크리트 | 다른 지면 메시(모래/풀) + 다른 랜드마크 | ← `project_world_biomes` 바이옴 순서 |
| M3 거리 직선 | BR 도로 | 흙길/모래길 변형 | 〃 |
| M5/M6 건물 | BR/Construction 건물 | 바이옴별 구조물(천막/폐기지 등) | 〃 |
| M8 랜드마크 | 고가 잔해 | 바이옴별 메모러블 피처(좌초선/송신탑 등) | ← 레퍼 §4 |

⚠️ **키트 스왑 = 그레이박스 1차 범위 아님.** 1차는 폐허 도심 1바이옴만. 키트 스왑은 모듈 시스템이 *재사용 가능하게 설계됐다*는 증명이지, 1차에 다 만든다는 뜻 아님(스코프 §7). **1차에서 "바이옴 불변/가변 경계를 모듈 데이터에 박아두는 것"까지만** = 후속 바이옴이 싸지는 토대.

## 7. 스코프 정직 (솔로 그레이박스)

### 7.1 라이브러리 청크 수 + 솔로 일수 현실 감

| 항목 | 1차 그레이박스 범위 | 비고 |
|---|---|---|
| **모듈 타입** | 12 타입(§1.1 전부) | 타입 자체는 적음 |
| **실제 프리팹 변종** | **~20개**(직선3·코너2·진입건물2·외관건물3·골목2·광장2·추출3·랜드마크1·봉쇄벽2) | Hades 수십 개 대비 의도적 축소 |
| **조립 알고리즘** | 규칙 명세(§3) → Gameplay C# 구현 | LevelDesign=규칙, Gameplay=코드 |
| **추정 작업** | **모듈 손제작 ~3일 + 조립규칙 명세→구현 협업 ~2일 + 검증/튜닝 ~1일 = ~6일** | 직전 고정 한 장(~5일)보다 +1일, **단 바이옴 재사용으로 분할상환** |

**자르기 우선순위(1차 더 줄여야 하면):**
1. **추출구 3종 → 2종**(X1 개방 + X3 플레어 먼저, X2 키 2차). ← 직전 설계 P3 동일.
2. **진입 건물 M6 → 1종**(파사드 M5 위주, 진입 가능은 X2 출구 1동만).
3. **고가 잔해 M8 → 박스 프록시**로 그레이박스, 실메시는 톤게이트 후.
4. **조립 알고리즘 → "수동 시드 3장"으로 시작**: 완전 절차 구현 전, 손으로 3가지 시드 레이아웃을 미리 짜두고 런마다 로테이션 = *절차 조립의 MVP*(Dead Cells도 초기엔 작은 풀). 진짜 절차 조립은 그 다음.

### 7.2 ★스코프 정직 경고 (솔로가 반드시 알 것)

- **"매 런 다른 오픈 존"은 공짜가 아니다.** 진짜 절차 조립기(§3 7단계 C#)는 *중간 복잡도 시스템*이다(엣지 매칭·불변식 보장·NavMesh 재베이크·시드 결정론). LevelDesign이 규칙은 다 줬지만 **구현 무게는 Gameplay 몫이고 작지 않다.** → **§7.1 자르기 4번(수동 시드 3장)으로 시작 강력 권고** = 절차 조립의 *재미*를 먼저 검증하고, 검증되면 진짜 조립기 투자.
- **측정 의존 변함없음**: 공간이 의도대로 읽히는가(누비기·동심원 노출감·추출 비대칭·콘 매복·매 런 다름 체감)까지만 캡처/플레이 검증. **쫄깃한가는 전투감(게이트0: 인식 3상태·피격 사다리·히트스탑) 선행 필수**(← run_structure ④ 압박엔진 의존성: "한 마리 안 무서우면 밀도 올려도 무해함만 많아짐"). **맵은 무대, 전투감이 배우.**

## 9. Owner 경계 + 핸드오프 (LevelDesign → Gameplay)

### 9.1 Owner 경계

**LevelDesign author(본 문서)**: 모듈 타입·역할·풋프린트·배치 띠 / 엣지 소켓 규약 / 조립 7단계 규칙 + 불변식 6 / 스폰 출처 분산 규칙 + 인구 예산 상한 / 드레싱 산포 규칙 / 변주 4겹 매핑 / 바이옴 가변·불변 경계 / 키트 실선별 / NavMesh 검증 포인트 / 시드 *값* 소유.

**Gameplay 구현**: 모듈 프리팹 제작(키트 조립) / `SpawnPointMarker` 부착 / **절차 조립기 C#**(§3 7단계, 엣지 매칭·불변식 보장·시드 결정론 소비) 또는 §7.1-4 수동 시드 로더 / SpawnDirector(스태거·복귀각성·디렉터20%) / 추출구 3종 런타임(키 게이트·플레어 타이머·개방 즉시) / 구역전이 proximity 트리거 / **NavMesh 베이크+이음새 검증+`isNavMeshValid` 스탬프(매 조립 후 재베이크)** / 풀 사이즈(동시 최대 alive 도출) / 추출구 셔터 off-mesh link.

### 9.2 NavMesh 검증 포인트 (조립 후 매번)

- **V1 모듈 이음새**: 인접 모듈 경계 NavMesh 연결성(0.01u 갭 = #1 버그). **그리드 스냅 + 바닥 0.5m 오버랩이 1차 방어**, 그래도 매 조립 후 재베이크+검증.
- **V2 추출구 셔터**: X2 키 출구 문/셔터 NavMesh 또는 off-mesh link.
- **V3 골목/알코브 연결**: M7 막다른 포켓도 본선 연결(매복체가 못 나오는 막힌 포켓 금지, 입구 ≥3m).
- **V4 비균일 스케일**: 모듈 내 프리팹 비균일 스케일 = NavMesh 오베이크. 금지.
- **V5 off-zero-Y**: 모듈 바닥 전부 Y=0(Construction 콘크리트 확인됨).
- **V6 스폰 분리**: 스폰 마커 최소 1.5m 분리(오버랩 폭발 방지).
- **V7 walkable 밀도**: ~1 agent/15㎡ 상한. 90×90=8100㎡ 중 walkable(건물 제외 ~60%≈4860㎡) → 동시 최대 ~324 이론 상한이나 실전은 띠 인구예산이 훨씬 낮게 캡. 조립이 예산 강제.

### 9.3 시계 분리 (공유 클락 드리프트 방지)

**구역 전이/추출 트리거 = proximity. 작전 타이머(폭격)/위협 레벨 = 별개 글로벌**(← run_structure ★개정: 위협 레벨이 시간·룰렛·강화 굴림, 별도 HUD 시계 ❌). 조립은 공간만 — 시계는 Gameplay 시스템.
